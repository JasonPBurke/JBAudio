# 03 — Three finish branches still hand-roll the mark and the transport

**What's wrong:** Tickets `01` and `02` unified the *rewind* half of finishing a
Book behind two named verbs. The other two halves — marking it `Finished` and
the transport calls that follow — are still open-coded at each of the three
sites, and after `02` two of them are near-line-for-line twins.

**Status:** resolved — `helpers/markBookFinishedOnce.ts`, 2026-08-30. `tsc` 0
errors, `eslint` 0 errors, full suite 87 suites / 1084 tests green.

> **Implementation note — where the caller tests mock.** The Traps section
> below says the existing finish tests must mock the NEW module. They do not,
> and deliberately: its premise ("they assert against a call the code no longer
> makes") does not hold here, because the verb still reaches `getBookById`,
> which both suites already mock. Letting the real verb run keeps every
> existing mark assertion meaningful instead of restating it as
> "markBookFinishedOnce was called", and it is what makes the reject-the-write
> acceptance test assertable from the CALL SITE, where the loss actually is —
> the transports and the rewind below the mark. The trap's precedent
> (`activeBookFootprints`) is different: the module underneath it does not
> resolve in the node lane at all.

**Found:** 2026-08-30, in the two-axis review of ticket `02`, as the Standards
axis's strongest finding (Duplicated Code).

## The evidence

`helpers/relativeSeek.ts`'s `seekForward` finish branch and
`helpers/nextPress.ts`'s `case 'finish'` now run the same five steps in the same
order: store-guard the mark, `getBookById` → `updateBookProgress(Finished)`,
`seekTo(0)`, `pause()`, swallowed rewind. **The comments are duplicated too**,
and one of them has to name the other copy to justify itself:

> `// … the same reading, for the same reason, as the finish branch in`
> `// helpers/nextPress.ts: a jump that lands inside the book-end lead window …`

A comment that can only explain itself by pointing at its twin is the smell. The
third site, `Event.PlaybackQueueEnded` in `setup/service.ts`, shares the guarded
mark but diverges on the transport (it `stop()`s rather than `pause()`s, and
branches `seekTo(0)` vs `skip(0)` on the queue shape).

## Why it was not folded into 02

`02`'s `## Scope` says *"No new modules, no new decisions"*, and this is both.
The two sites obtain the Book differently — `relativeSeek` looks it up in the
library store because it only knows the Active Book id; `handleNextPress` takes
it as an injected parameter, which is what makes its ordering assertable without
a store. Collapsing them means deciding which shape wins, and that is a design
call rather than a tidy-up. `02` recorded it instead of smuggling it in.

## Triage Notes — 2026-08-30

> *This was generated by AI during triage.*

**Question from the maintainer:** are the transport differences accidental —
same observable outcome by different means — and is this ticket consolidating
them?

**Answer: half accidental, half a real behavioural divergence. This ticket
consolidates NEITHER, and should not.**

### The position half IS the same outcome by different means

| Site | Position calls |
| --- | --- |
| `relativeSeek.ts` finish | `if (shape.index !== 0) skip(0)` **then** `seekTo(0)` |
| `nextPress.ts` `case 'finish'` | `seekTo(0)` only |
| `service.ts` `PlaybackQueueEnded` | `isSingleFile ? seekTo(0) : skip(0)` |

All three land at item 0, position 0. They differ because each was written
against the queue shapes that can REACH it: `nextPress`'s finish is only
reachable for a single-item queue (`resolveNextPress` returns `finish` only on
the last chapter of a single-file Book), so it has no index to move;
`seekForward`'s finish is reachable from ANY shape, so it guards the skip;
`PlaybackQueueEnded` branches because it already has `isSingleFile` in hand.

`skip()` is documented in `player/trackPlayer.ts` as "Native resets the position
to 0", which makes `relativeSeek`'s trailing `seekTo(0)` redundant on the
multi-item path — the one genuinely accidental line in the table. Not worth a
ticket on its own; it is also the belt-and-braces that makes the single-item
path work.

### The `pause()` vs `stop()` half is NOT the same outcome

Traced to the native layer of the pinned RNTP alpha
(`kotlinaudio/players/BaseAudioPlayer.kt`):

```kotlin
fun pause() { exoPlayer.pause() }

open fun stop() {
    playerState = AudioPlayerState.STOPPED
    exoPlayer.playWhenReady = false
    exoPlayer.stop()   // releases the loaded media and playback resources
}
```

And in OUR code the resulting state routes to two different handlers
(`service.ts:663-669`):

- `State.Paused` → `sleepTimer.onPlaybackPaused()` — **freezes** the timer and
  persists `frozenRemainingMs`, so it survives to the next listen.
- `State.Stopped` → `sleepTimer.onPlaybackStopped()` — **cancels and clears**
  it: `timerActive = false`, frozen remaining nulled, store cleared.

So: finishing a Book by pressing Next on its last chapter, or by jumping past
its end, leaves a running sleep timer FROZEN. Finishing the same Book by
playing it to the true end DESTROYS the timer. Same Book, same "finished"
outcome, different sleep-timer state. `stop()` has exactly one caller in the
app — `service.ts:623`.

### ⚠ The drift evidence: a comment that contradicts its code

`nextPress.ts:107` reads:

> `// The stop is deliberate — unlike the 1 Hz lead-time mark, this is a`
> `// user press asking to leave the last chapter, and there is nowhere`
> `// left to play.`

The code two lines below calls `pause()`. One of the two is wrong, and which one
is a decision about the sleep timer, not a typo. **Filed as ticket `04`.**

### Scope ruling for THIS ticket

Unchanged and narrow: `markBookFinishedOnce` and nothing else. The transports
stay duplicated on purpose — they encode per-site decisions (reachable queue
shapes; whether the timer survives), and collapsing them would hide the very
divergence `04` now exists to settle. This ticket must not touch `pause`/`stop`.

**Ordering:** `04` was ruled on and is `ready-for-agent` while this ticket is
still waiting on a design answer, and the two edit adjacent lines in the same
two finish branches. **`04` lands first; `03` rebases onto it.**

## Ruling — DRIVER-DECIDED, 2026-08-30

1. **`markBookFinishedOnce(bookId, book)`, with `book` injected.** The store read
   stays at the caller. This keeps `handleNextPress`'s ordering property
   assertable without a store, which is the reason that function takes its Book
   as a parameter in the first place. What remains duplicated is a store LOOKUP,
   not a guard — and a lookup is not the thing that drifts.
2. **The missing `try/catch` rides along in this ticket.** The extracted verb
   owns the swallow, so no caller can reach the mark without it.

### ⚠ Correction to this ticket's earlier triage notes

An earlier reading here said three of the four mark sites were unguarded against
a throw. That was wrong, and the truth is a better argument for the extraction:
`seekForward`'s finish branch **does** swallow — its whole mark block sits inside
`withoutBlockingThePress`. The two genuinely unguarded sites are
`handleNextPress`'s `case 'finish'` and `Event.PlaybackQueueEnded`. So the
swallow exists at one site as an outer wrapper, is absent at two others, and
`applyBookEndDecision` spells it a third way with its own `try/catch` and a
`console.error`. Three spellings, two of them missing. Making the swallow
intrinsic to the verb is what removes the choice.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement (carries one robustness fix)
**Summary:** Extract the store-guarded "mark this Book Finished" step into one
named verb that owns its own failure handling, and route the three finish
branches through it.

**Current behavior:**
Three code paths finish a Book — the skip-forward press's finish branch, the
forward relative-seek's finish branch, and the playback service's queue-ended
handler. Each opens with the same guarded mark: read the Book's progress value
from the library store, and only if it is not already `Finished`, look the Book
model up by id and set its progress to `Finished`. The guard protects
`finished_at` from being rewritten by a press that lands inside the book-end
lead window, where the 1 Hz tick has already marked the Book.

The three copies agree today but are maintained by hand, and their failure
handling does not agree: one wraps the mark in the shared
"don't block the press" swallow, two let a throw escape. `updateBookProgress` is
a raw WatermelonDB writer that throws if the row was destroyed underneath it by
a concurrent scan. At the two unguarded sites the escape aborts the position
reset, the transport call and the chapter-tracking rewind that follow, and
surfaces as an unhandled rejection — none of the four call sites catches.

A fourth site marks a Book Finished from the progress tick. It is NOT part of
this family: its guard is a process-lifetime latch rather than the store, it
must latch only after the write lands, and it already has its own `try/catch`.

**Desired behavior:**
One exported verb — `markBookFinishedOnce(bookId, book)` — in a small module of
its own, holding the guard and the mark and nothing else:

- `book` is the caller's library-store entry for `bookId`, and is legitimately
  `undefined` on the cold-start path. An absent or non-`Finished` progress value
  means the mark proceeds.
- It resolves the Book model by id and sets progress to `Finished` only when the
  guard passes.
- It never throws. A failure is swallowed and logged, matching how the
  progress-tick marker already reports the same failure.
- It performs no seek, skip, pause, stop or chapter-tracking rewind. Those stay
  at the call sites, where they legitimately differ.

All three finish branches call it and keep their own transports and their own
rewind, in their current ORDER. The forward relative-seek's finish branch reads
its Book from the library store itself (it only knows the Active Book id) and
passes it in; the other two already hold a Book.

**Key interfaces:**
- `markBookFinishedOnce(bookId: string, book: { bookProgressValue?: number } | undefined): Promise<void>`
  — the widest parameter type that satisfies all three callers; do not require a
  full `Book`, since the guard reads one field.
- The Book model's `updateBookProgress` and the `getBookById` lookup move behind
  this verb. After the change, neither the skip-forward press module nor the
  relative-seek module should import `getBookById` or the progress-state enum
  for this purpose.
- `withoutBlockingThePress` — the relative-seek site's outer wrapper around its
  mark becomes redundant once the verb owns the swallow, and should go. The
  wrapper stays where it guards the chapter-tracking rewind.

**Acceptance criteria:**
- [ ] Exactly one place in the codebase performs a store-guarded
      `Finished` mark; the three finish branches call it.
- [ ] The verb swallows and logs a throw from the underlying write. A test
      forces the write to reject and asserts the caller's transport calls still
      run in their normal order.
- [ ] A test asserts the guard: a Book whose store entry is already `Finished`
      is not re-marked.
- [ ] A test asserts an `undefined` Book still marks.
- [ ] The existing ordering assertions on both press finish branches still pass
      — leave-the-Book footprint first, chapter-tracking rewind LAST.
- [ ] The progress-tick marker is unchanged: still latch-guarded, still latching
      only after the write lands, still its own `try/catch`.
- [ ] `npm run lint` and `tsc` stay at zero errors.

**Out of scope:**
- The transport calls. `pause`/`stop` is ticket `04` and lands first; the
  position calls (`skip(0)` / `seekTo(0)`) differ per reachable queue shape and
  converge on the same result — leave both alone.
- Folding the progress-tick marker into the new verb. Its latch-after-write
  invariant is incompatible with a verb that swallows, since the caller could
  not tell whether the write landed. If a later ticket wants this, the verb has
  to return a result first — do not add one speculatively.
- The chapter-tracking rewind. It is already shared; its two spellings
  (the wrapper that uses the module singleton, and the inner form that takes an
  injected tracker) are deliberate and testability-driven.

**Traps:**
- ⚠ **Mock the HELPER, not the query module underneath it.** The existing finish
  tests mock `@/db/bookQueries`'s `getBookById` to observe the mark. Once the
  mark moves behind the new verb, those tests must mock the new module instead,
  or they will assert against a call the code no longer makes and pass while
  testing nothing. This repo has been bitten by exactly this before — see the
  Active-Book footprint helper's tests.
- These are helpers-lane tests (plain `*.test.ts`, node, no RN preset). Keep
  them there; nothing here needs the `rn` lane. Read
  `docs/testing/jest-projects-and-rn-tests.md` first.
- The queue-ended handler's mark currently sits after its chapter-index writes
  and before its transport calls. Preserve that position — moving the mark
  earlier changes what a concurrent progress tick can observe.
