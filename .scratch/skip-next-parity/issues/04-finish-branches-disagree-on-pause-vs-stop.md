# 04 — The finish branches disagree on `pause()` vs `stop()`

**Status:** resolved — code complete 2026-08-30, `tsc` 0 errors, `eslint` 0
errors, jest **1075/1075** (86 suites). Both press-driven finish branches now
call `stop()`; `helpers/nextPress.ts`'s finish comment matches its code again.
⚠ The two DEVICE rows below are still OPEN: the sleep-timer clear and the
re-prepare-after-`stop()` play are what this change is actually about, and
neither is observable from the node lane.

**Found:** 2026-08-30, during the triage of ticket `03`, when the maintainer
asked whether the transport differences between the three finish branches were
accidental. The position differences are. This one is not.

## What's wrong

Three sites finish a Book. Two `pause()`, one `stop()`. That is not a stylistic
difference — in the pinned RNTP alpha the two calls diverge natively, and in our
own service they route to two sleep-timer handlers that do opposite things.

`kotlinaudio/players/BaseAudioPlayer.kt`:

```kotlin
fun pause() { exoPlayer.pause() }

open fun stop() {
    playerState = AudioPlayerState.STOPPED
    exoPlayer.playWhenReady = false
    exoPlayer.stop()   // releases the loaded media and playback resources
}
```

`setup/service.ts:663-669` then routes the resulting state:

- `State.Paused` → `sleepTimer.onPlaybackPaused()` — **freezes** the timer,
  persisting `frozenRemainingMs` so it survives to the next listen.
- `State.Stopped` → `sleepTimer.onPlaybackStopped()` — **cancels and clears**
  it: `timerActive = false`, frozen remaining nulled, store cleared.

## The observable defect

With a sleep timer running, the same Book reaching the same finished state
leaves the timer in two different conditions depending on HOW it finished:

| How the Book finished | Transport | Sleep timer after |
| --- | --- | --- |
| Next pressed on the last chapter (`nextPress.ts`) | `pause()` | **frozen**, resumes on next play |
| 30s jump past the end (`relativeSeek.ts`) | `pause()` | **frozen**, resumes on next play |
| Played through to the true end (`service.ts`) | `stop()` | **cleared** |

A user who falls asleep with a timer armed gets a different timer state
depending on whether the book ran out under them or they pressed a button — and
the frozen-timer case will later resume a countdown against a **different Book**,
since the finished one has been rewound to 0 and the next thing they play is
something else. `stop()` has exactly one caller in the app (`service.ts:623`).

## ⚠ The comment that contradicts its code

`helpers/nextPress.ts:107`, inside `case 'finish'`:

> `// Last chapter of a single-file Book: mark finished, reset and pause.`
> `// The stop is deliberate — unlike the 1 Hz lead-time mark, this is a`
> `// user press asking to leave the last chapter, and there is nowhere`
> `// left to play.`

The code calls `pause()`. The comment argues for a `stop()`. **The comment is the
correct half** — see the ruling below. The tempting fix, editing the comment to
match the code, would have silently ratified the drift.

## The ruling — DRIVER-DECIDED, 2026-08-30

Asked whether the divergence was deliberate, the driver's answer was that it was
**not**: the two calls were written at different times, the intent at every site
is the same — *"if a book finishes, it should reset to the start of the book and
stop playing"* — and both calls satisfy that intent as heard through the
speaker, which is why the inconsistency survived. Ruling:

> **Replace `pause()` with `stop()`. All three finish branches stop.**

This retires the three-way question this ticket opened with. `nextPress.ts`'s
"the stop is deliberate" comment turns out to record the original intent
faithfully; the `pause()` under it is the drift.

⚠ **The rider the transport call hides.** The audible behaviour is identical, so
the change looks cosmetic and is not: moving those two sites to `stop()` moves
them from `sleepTimer.onPlaybackPaused()` to `sleepTimer.onPlaybackStopped()`,
so an armed sleep timer that used to be **frozen** by a press-finish will now be
**cleared**. That is a deliberate consequence of the ruling — a finished Book
ends the listening session, and a frozen timer would otherwise resume later
against a different Book — but it is the one user-visible change here and the
thing to verify on device.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** The two press-driven finish branches pause where they should stop,
so finishing a Book by pressing Next (or by jumping past its end) leaves the
player and the sleep timer in a different state than playing the Book to its end.

**Current behavior:**
Three code paths finish a Book: the skip-forward press's finish branch, the
relative-seek forward helper's finish branch, and the playback service's
queue-ended handler. All three mark the Book `Finished` and reset it to position
zero. The first two then call the player's `pause`; the third calls `stop`. The
divergence is unintentional. Because the service's playback-state subscriber
routes `Paused` and `Stopped` to two different sleep-timer entry points, an
armed sleep timer is frozen and persisted when a Book is finished by a press,
but cancelled and cleared when the same Book finishes by playing out.

**Desired behavior:**
All three finish paths call the player's `stop`, so that finishing a Book leaves
one state regardless of how it was finished: position zero, playback halted,
sleep timer cleared. No other part of the finish sequence changes — the
already-`Finished` guard, the mark, the position reset and the chapter-tracking
rewind all keep their current behavior and their current ORDER.

**Key interfaces:**
- The player seam's `stop()` wrapper — already exported alongside `pause()`; no
  new wrapper is needed. Before this change it had exactly one caller.
- The playback service's `Event.PlaybackState` subscriber — unchanged, but it is
  what makes this a behavioral fix rather than a rename: it maps `State.Paused`
  to the sleep timer's paused handler (freeze + persist `frozenRemainingMs`) and
  `State.Stopped` to its stopped handler (cancel, clear `timerActive`, clear the
  store).
- The `case 'finish'` branch of the skip-forward press decision, and the
  `kind: 'finished'` branch of the forward relative seek. Both are reachable
  only when a Book has actually ended.

**Acceptance criteria:**
- [x] No finish path calls `pause`; every path that finishes a Book calls `stop`.
- [x] `pause` is still used by the ordinary play/pause control — this change
      does not touch any non-finish caller.
- [x] The existing call-ORDER assertions on the finish branches still pass: the
      leave-the-Book footprint is recorded first, the mark is guarded on the
      store, and the chapter-tracking rewind runs LAST.
- [x] A test asserts the finish branches call `stop` and not `pause`. The fake
      player harness is the place for it.
- [x] `nextPress`'s finish comment no longer describes a call the code does not
      make.
- [ ] Device: with a sleep timer armed, pressing Next on the last chapter of a
      single-file Book clears the timer, matching what playing that Book to its
      true end already does.
- [ ] Device: after a Book finishes this way, pressing play again starts it from
      the beginning. `stop` releases the loaded media, so this path re-prepares
      the source — confirm there is no error or stuck state, only latency.

**Out of scope:**
- The position calls. `skip(0)` / `seekTo(0)` differ between the three sites for
  a real reason — each was written against the queue shapes that can reach it —
  and converge on the same result. Leave them alone.
- Extracting the shared finished-mark. That is ticket `03`.
- Any change to the sleep timer's own freeze/clear semantics. This ticket only
  changes WHICH of the two existing handlers these paths reach.
- The notification's behavior on `Stopped` was not characterized during triage.
  If it visibly changes, file it rather than fixing it here.

## Resolution — 2026-08-30

**Source (2 call sites, 2 identifiers):**

- `helpers/nextPress.ts` — `case 'finish'`: `await pause()` → `await stop()`;
  the import moved from `pause` to `stop`. The "the stop is deliberate" comment
  is kept and extended with the half it never stated: `stop()` is what reaches
  `sleepTimer.onPlaybackStopped()`.
- `helpers/relativeSeek.ts` — `kind: 'finished'`: same swap. `pause` was this
  module's only use of that import, so the import is gone; the play-state guard
  is still skipped on this branch, as before.

Nothing else in either finish sequence moved: the already-`Finished` store
guard, the mark, `skip(0)`/`seekTo(0)` and the LAST-position chapter rewind all
keep their order.

**Tests:**

- `__tests__/support/fakePlayer.ts` gained a `stop` that halts playback. It does
  NOT model native's release of the loaded media — nothing here can observe it,
  and pretending otherwise would invite a test that asserts a fiction.
- `nextPress.test.ts`: the RNTP mock now records `stop` into `mockOrder`, the
  four finish order-arrays read `stop`, and the main finish test asserts
  `pause` was never called at all.
- `relativeSeek.test.ts`: same, plus the three finish assertions that counted
  `pause` calls now count `stop`. "does not force play after the intentional
  finish-pause" is renamed to `…finish-stop` and also asserts no `pause`.
- `relativeSeek.shortChapters.test.ts` gained a `stop` passthrough — its mock
  would otherwise hand `undefined` to any test that reaches a finish branch.

**Still open — device verification.** The two device rows in the acceptance
