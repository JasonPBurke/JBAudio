## The defect

`electDisplayNames` (`src/helpers/seriesDetection.ts`) gathers folder candidates with:

```ts
for (let d = 1; d < parts.length - 1; d++) candidates.push(cleanDirName(parts[d]));
```

`parts` comes from `a.unit.rel`, which is the book's **DIRECTORY** relative to the library root —
never the file (see the `DetectionUnit.rel` doc comment). So both bounds are positional, and the
window they leave open depends on how deep the user's root sits:

| library root | `rel` for the same book | folder candidates |
| --- | --- | --- |
| `/Audiobooks` | `Terry Pratchett/Discworld/Reaper Man` | `Discworld` ✅ |
| `/Audiobooks/Terry Pratchett` | `Discworld/Reaper Man` | **none** — `d = 1; d < 1` runs zero times |
| `/Audiobooks/Terry Pratchett` (flat) | `Discworld` | **none** |

Same books, same tags, different display name — decided by a setting that is meant to be about
*where files live*, not about what they are called. When no folder qualifies, the name falls back
to the tag-parsed `a.name`, so the folder's tidier spelling can never win.

⚠ **This is the exact defect class `folderClusters`' header describes and says was FIXED there**:
depth is "a fact about where the user pointed their library root, not about the books". Rooting at
`/Audiobooks/Terry Pratchett` once already merged 47 Discworld editions into one series. That rule
was removed from clustering; `electDisplayNames` is where it survived.

## ⚠ Do NOT "fix" this by starting the loop at 0 — that is a different, worse bug

Measured 2026-08-14, all three variants against the 73-test detection suite:

| variant | result |
| --- | --- |
| `d = 0; d < parts.length - 1` | **2 failed** |
| `d = 0; d < parts.length` | **2 failed** |
| `d = 1; d < parts.length` | 73 passed (corpus-neutral) |
| shipped `d = 1; d < parts.length - 1` | 73 passed |

`parts[0]` is the **author level**. Including it elects **`Martha Wells`** over
**`The Murderbot Diaries`**. The `d = 1` start is the author guard and must not be removed without
a replacement.

## What a real fix has to do

Refuse author folders on the **tags** rather than on **position**, the way clustering already does
(`isAuthorish`, which works at every depth). That was measured too, and it is **not a drop-in**:

- ✅ It fixes the author case properly — Murderbot stays correct.
- ❌ It still fails `A1 · extra.SERIES outranks a disagreeing album pattern`, and the reason is a
  **second, independent weakness**: the candidate filter accepts anything satisfying
  `key.includes(ck)`, so the one-character fixture folder `A` qualifies as a candidate for
  `The Expanse` (`'expanse'.includes('a')`), and the *shortest-wins* tie-break elects `A`.

So the fix is two changes, not one: tag-based author refusal **plus** a length/containment guard on
candidates so a short folder cannot impersonate a long series name.

## Acceptance criteria

- [ ] The elected display name is **identical** for the same books under two different library
      roots (one and two levels up). This is the criterion; a test with two `rel` shapes pins it.
- [ ] `The Murderbot Diaries` still beats `Martha Wells`, by a **tag-based** refusal.
- [ ] A one-character or otherwise degenerate folder cannot be elected over a real series name.
- [ ] The corpus baseline is unmoved: **19 series / 179 books conservative, 28 / 213 full**, and
      A4's 80-book Discworld split still lands at 41 + 39.
- [ ] jest green · `tsc` 0 errors · eslint 0 errors.

### Triage, 2026-08-15 — `bug`, parked as `needs-info`

> *This was generated by AI during triage.*

**Verdict: the defect is CONFIRMED by reproduction, and the category is `bug`. It is parked
rather than briefed because the fix direction this ticket states as settled is NOT settled —
implementing both prescribed changes was measured and it REGRESSES the corpus. Three findings
below were not in the ticket; the third is the one that matters most.**

#### 1. The reproduction (CONFIRMED)

Built on the existing `TMC Saga` fixture, because it is a case where the folder holds the
tidier spelling. Same books, same tags, only `rel` differs:

| `rel` | elected display name |
| --- | --- |
| `Robin Hobb/TMC Saga/Ship of Magic` | `TMC Saga` ✅ |
| `TMC Saga/Ship of Magic` | **`TMC`** ❌ |

Baseline before and after the probe: **73 passed**, working tree restored clean.

#### 2. ⚠ The blast radius is NARROWER than this ticket's table — a test written from that table can go VACUOUSLY GREEN

The table in **The defect** is about *candidates*, not about the elected *name*. The elected
name only changes when a folder would actually have WON the election — i.e. when the folder
carries a better spelling than the tags do. Measured counter-example: books tagged
`Discworld 11 - Reaper Man` under `Terry Pratchett/Discworld Novels/…` elect **`Discworld` at
BOTH depths**, because the tag already supplies the winning name.

**So acceptance criterion 1 ("identical under two roots") is right, but the fixture that pins it
must be one where the folder spelling wins.** A Discworld-shaped fixture passes against the
UNFIXED code and proves nothing. Same failure mode as ticket 27's window test.

#### 3. ⚠ `electDisplayNames` REWRITES THE GROUP KEY — it is a grouping pass, not a labelling pass

`seriesDetection.ts:613-617` sets `a.key = normKey(elected)` on every member, and
`detectSeries` then buckets proposals by exactly that key (`:761`). **Two groups whose elected
names normalise to the same key MERGE.** This is why a change that reads as cosmetic can move
detection output, and it is the fact that makes this ticket riskier than it looks.

#### 4. ⚠ The prescribed two-part fix was measured and it MOVES THE CORPUS

All variants against the 73-test detection suite:

| variant | result |
| --- | --- |
| shipped `d = 1; d < parts.length - 1` | 73 passed |
| naive `d = 0; d < parts.length - 1` | **2 failed** — exactly the two this ticket names ✅ |
| `d = 0` + tag-based author refusal + a `ck.length >= key.length * 0.5` containment guard | the two named tests **PASS**, but **2 corpus tests fail** |

The corpus failure is the important half: `numberAccuracy(conservative())` goes
**`{correct: 162, scored: 168}` → `{correct: 158, scored: 164}`**.

`scored` only counts a book when `scoringKey(p.name) === scoringKey(t.series)`
(`seriesDetection.corpus.test.ts:77`), so **`scored` falling by 4 means four books' series are
no longer named their ground-truth name.** The author refusal is the easy half; the
**containment guard is the hard part**, and a flat length ratio is too blunt.

#### 5. ⚠ THIS TICKET'S ACCEPTANCE CRITERIA CANNOT SEE THAT REGRESSION

Under the variant in row 3 above, **every criterion this ticket lists was still GREEN** — 19/179
conservative, 28/213 full, and A4's 41+39 Discworld split. The four mis-named books were
invisible to all of them.

**Any future brief MUST add, as a criterion in its own right:**

```
numberAccuracy(conservative()) === { correct: 162, scored: 168 }
```

and must **forbid moving the `0.964` and `0.983` thresholds** in
`describe('threshold assertions on the conservative tier')`. The probe landed at **0.9634**
against a `>= 0.964` assertion — one threshold nudge away from a fake green.

#### What we still need (@driver)

1. **Is a display-name fix allowed to move grouping at all?** Finding 3 means the two cannot be
   fully separated. If the answer is no, the fix must additionally prove the proposal set is
   unchanged, which is a stronger bar than anything written here today.
2. **What replaces the flat length ratio as the containment guard?** The requirement is: reject
   the one-character `A` for `The Expanse` while still accepting the four legitimate shorter
   folder spellings that finding 4 knocked out. Naming the four is the first job of whoever
   picks this up.
3. **Is this worth fixing at all right now?** It only bites a user who rooted their library at
   the author level *and* whose folders are better-spelt than their tags. No user report exists;
   it was found by code review. `wontfix` is a legitimate answer and would cost nothing but this
   comment.

#### What this means

- **Fixing this ticket buys 0 measurable accuracy on the real library.** 57% of the corpus can
  lose its folder vote outright and not one book moves.
- The reason is that **the tags on this library already carry the series name**; the folder vote
  is almost never the deciding one. Where it does decide, it is worth an article or a full stop.
- ⚠ **The direction of harm is not even consistent** — `The Dresden Files` is arguably the BETTER
  name, and it is the deep-rooted result. "Folder spelling is tidier than tags" is an assumption
  this ticket makes and the corpus does not support.
- Against that, the only measured accuracy movement in this whole ticket is **downward**: the
  prescribed fix cost 4 books their correct name.

**Recommendation upgraded to `wontfix`**, pending the driver. Reopen only on a real user report
of a wrongly-named series in a library rooted below the author level.

⚠ **Honest limit of this evidence:** the corpus is one real library with GOOD TAGS. A library
with poor tags and tidy folders would lean on the folder vote much harder, and nothing here
measures that. The conclusion is "no impact on the library we can measure", not "no impact
possible".
