## The defect

`seriesEditorIssues` refuses a save with `bookCount === 0` and tells the user
*"Add at least one book, or use Delete Series to remove it."*

`bookCount` is `orderedBookKeys.length` (`seriesEditor.tsx`), seeded from `visibleKeysOf(series)`
— the books that **resolve against the live library**. So a series whose files are *all*
temporarily unresolvable reports zero books:

- an SD card unmounted,
- a folder mid-move,
- a rescan that has not caught up.

`scanLibrary` treats exactly that state as legitimate and expected — its orphan prune is gated
on `orphanedBooks.length > 0` precisely so a moved file's rows survive until a scan proves the
book is gone. Ticket 21 went to some length to stop `Save` destroying those rows.

**The result:** the user cannot even rename the series, and the only action the message names is
`Delete Series`, which permanently destroys every membership row and writes A12's suppression.
A fully recoverable state is being steered toward the irreversible action.

## ⚠ Why this is not `ready-for-agent`

**The unconditional book requirement is a DRIVER RULING made on device on 2026-08-13** (ticket
16). It replaced an edit-mode exemption under which emptying a series and pressing `Save`
performed an unconfirmed destroy — K7 through the other door. The rationale is written out at
`seriesValidation.ts:48`, and A14's *bulk creates, per-item destroys* stands behind it.

Any fix here re-opens that ruling, so it needs the driver, not an agent.

## Directions, for that conversation

1. **Distinguish the two empties.** The screen already knows: an empty draft where
   `series.books` is empty AND the series has membership rows is *"nothing resolves"*, not
   *"the user removed everything"*. Validation would need that fact threaded in.
2. **Or gate the message, not the save.** Allow a rename when the list is empty only because
   nothing resolved, and keep refusing a save that would empty a resolvable series.
3. **Or say something truer.** Even leaving the refusal in place, pointing a user at
   `Delete Series` when their SD card is unmounted is the wrong sentence.

Do **not** simply drop the `bookCount === 0` check — that restores the unconfirmed destroy.

## Comments

### Triage, 2026-08-15 — `wontfix`

> *This was generated by AI during triage.*

**Verdict: closed as `wontfix`. The defect is real in the narrow sense that the code does what
this ticket says it does — but every route it names to that state is refuted, and the one
surviving route is a lab setup, not a user story. Ticket 16's driver ruling is NOT reopened.**

#### What was verified first

The symptom reproduces, *given the state*. Driving the real chain
(`assembleDerivedSeries` → `visibleKeysOf` → `seriesEditorIssues`) with one series, three
membership rows, and only the library book map varying:

- books resolve → rename saves clean, `issues === []`;
- books absent → `visibleKeysOf` is `[]` and the save is refused with exactly
  `'Add at least one book, or use Delete Series to remove it.'`;
- adding any one resolvable book unblocks it (the workaround exists, and it is safe — with
  `visibleAtSeed === []` ticket 21's rule means the save may touch nothing but the name).

The series also survives that far: `assembleDerivedSeries` **maps, never filters**
(`seriesAssembly.ts:117`), so it stays on the browse list with `books: []`, and
`MissingSeries` does not fire because that needs `!series` (`seriesDetail.tsx:44`). So the
editor is reachable and the refusal is real.

**⚠ That is reachability of the SYMPTOM GIVEN THE STATE, which is not what the ticket needed
to establish.** The state itself is the claim, and it does not hold.

#### Why each stated scenario is refuted

**1. "An SD card unmounted" — REFUTED, and it fails for the OPPOSITE reason to the obvious
one.** The scan builds `availableRoots` from `RNFS.exists` (`scanLibrary.ts:921-926`) and then
skips every chapter under a root that is not available:

```ts
if (root !== undefined) {
  if (!availableRoots.has(root)) continue;   // scanLibrary.ts:936 — never queued for removal
```

Nothing is queued, nothing orphans, nothing is pruned — **the books stay in the database.**
They therefore stay in the library store's book map, their structural keys still resolve, and
`assembleDerivedSeries` returns the series **with all of its books**. `bookCount > 0` and the
refusal never fires. An unmounted volume does not empty a series; it does not empty anything.
The guard is deliberate and documented as load-bearing at `scanLibrary.ts:1009-1013`:
*"renaming your library folder destroys nothing while moving its contents out of it destroys
everything."*

⚠ The intuition this refutes cuts both ways, so it is worth stating plainly: **a rescan with
the card pulled does NOT purge those books from the library.** Do not reason from the opposite
belief elsewhere.

**2. "A folder mid-move" — REFUTED on two counts.** Moving a folder is done in a Files app, so
this app is backgrounded and no scan can run at all (driver, 2026-08-15). And when the move
completes and a scan *does* run, the outcome is still not an empty-but-present series: the
books orphan, the gate at `scanLibrary.ts:1014` fires, `pruneOrphanedSeriesBooks` destroys the
membership rows and `deleteEmptySeries` reaps the series. It is **gone, not empty** — there is
no editor left to open.

**3. "A rescan that has not caught up" — REFUTED as incoherent.** Scans are foreground and
synchronous here; there is no partial-visibility window for the phrase to name. It does not
survive contact with the code, and it was carried into the ticket without one.

#### The one real mechanism, and why it does not rescue the ticket

A row *can* dangle indefinitely, and it is documented at `scanLibrary.ts:1001-1003`: **rename
only the first file of a multi-file book.** The book survives on its remaining chapters, so
nothing orphans, so the gate never fires, and the row is left pointing at a dead path until
some later unrelated scan orphans any book. Real, deliberate, ADR-backed.

But this ticket's symptom needs **every book in the series** re-keyed that way while **no book
anywhere in the library** orphans. Dangling is reachable one row at a time and essentially
unreachable all at once — and all at once is the only thing that empties the editor.

#### Why the ruling is not worth reopening for it

The driver's position, and it is correct: if a user removes each book by hand, the only
coherent intent is to delete the series, and `Delete Series` is sitting on that same screen.
The refusal fires in two different situations, and the fix direction this ticket proposed
(refuse only when `visibleAtSeed.length > 0`) preserved that one untouched — it only relaxed
the case where the user had removed nothing because they were shown nothing. **With that second
case unreachable, the distinction costs a driver ruling and buys nothing.**

#### Two corrections owed to this ticket's own text

1. **"...and writes A12's suppression" is only half true.** `deleteSeries` gates the
   suppression row on `series.origin === 'detected'` (`seriesQueries.ts:458`). This inverts the
   severity the ticket argued: a **detected** series can be recovered through `Removed Series`
   + rescan (with a new id and detection's own name/numbers, so a rename and any hand-curated
   order are lost), while a **user-created** series gets no suppression precisely because
   nothing would ever recreate it — its rows and the series are destroyed with **no recovery
   path at all**. The worst case is the one the ticket's suppression argument does not cover.
2. **The framing "a fully recoverable state is being steered toward the irreversible action"**
   rests on the state existing. It does not, so the sentence describes nothing.

#### Open caveat, recorded rather than hidden

The three *named* routes are refuted; no exhaustive proof was constructed that **no** route
reaches a rows-but-zero-visible series. The one gap not chased: the all-tombstoned (K16) case
— `assembleDerivedSeries`'s comment notes `deleteEmptySeries` "must keep counting them", which
implies such a state is contemplated somewhere. It looks unreachable through the editor (every
save demands ≥ 1 book, so the count can never be driven to zero), but it was not chased through
the `Add to series…` join door.

**What would reopen this:** a real user report of a series that renders with no books, or a
route to the all-tombstoned state through the join door. Not a re-reading of the same three
scenarios.
